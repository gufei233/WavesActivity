# WavesActivity

WavesActivity 是 GsCore 的鸣潮钓鱼活动插件，依赖已安装的 XutheringWavesUID（下文简称 XWUID）。

发送 **`ww活动`**，插件读取发送者在 XWUID 当前选中的鸣潮账号和社区 token，完成本期活动并回复新增奖励。默认指令前缀为 `ww`；实际前缀跟随 XWUID 的配置。

## 功能与范围

- 完成分享、跳转任务，并领取任务奖励。
- 完成已开放的六个普通关和一个挑战关。
- 领取普通关首通奖励和宝箱奖励。
- 领取服务端判定达成的图鉴、挑战任务奖励。
- 跳过已完成项目；已通关但宝箱未领时重新开局补领。
- 回复关卡、宝箱、图鉴、任务完成数和本次新增奖励。

当前版本针对 `Fishing-20260930-Om6fxfxr` 钓鱼活动。原始活动时间为北京时间 **2026-10-15 10:00 到 2026-11-01 10:00**。插件在运行时查询活动状态；活动未进行时停止执行。

七关参数来自活动抓包和 2026-10-20 的完整运行记录。后续活动需要更新接口和关卡参数。

## 环境要求

| 项目 | 要求 |
|---|---|
| Python | 3.11 或更高版本 |
| GsCore | 支持嵌套插件、`on_core_start_before`、`on_core_start`、`on_core_shutdown` 和 `with_read_session` |
| XWUID | 已安装，且用户已登录并选择鸣潮账号 |
| Python 依赖 | `aiohttp>=3.9`；Pydantic 2、SQLModel 和 SQLAlchemy 使用宿主依赖 |
| 消息入口 | 机器人通过 WebSocket 接收的私聊或群聊指令 |

GsCore 的单次 HTTP 调用只能返回当前请求的结果，无法收取数分钟后的回复。通过 HTTP 调用本插件会收到改用机器人聊天的提示。

## 安装与更新

1. 将插件根目录放入 `gsuid_core/plugins/WavesActivity/`。
2. 确认 XWUID 已加载，且 GsCore 已安装 `pyproject.toml` 声明的依赖。
3. 发送管理员指令 `core重载插件WavesActivity`，或重启 GsCore。
4. 查看日志中的 `[鸣潮活动] 已注册指令：ww活动`。

安装后的目录应包含 `WavesActivity/WavesActivity/__init__.py`，避免多解压一层。

更新时覆盖同名插件目录，再重载插件。修改 XWUID 前缀后，先让 XWUID 加载新配置，再重载 WavesActivity。两种插件各自保留自己的权限和启用开关。

## 使用

1. 发送 `ww登录`，完成 XWUID 登录和绑定。前缀有变时使用对应的登录指令。
2. 在 XWUID 中切换到要执行活动的鸣潮账号。
3. 发送 `ww活动`。
4. 收到开始提示后等待最终回复。完整七关通常需要 5 到 6 分钟。

插件按 XWUID 的 `prefix`、启用的 `force_prefix` 和 `allow_empty_prefix` 注册完整指令。指令不接受账号参数；`ww活动 其他账号` 不会触发执行。

结果示例：

```text
[鸣潮活动] 活动已全部完成
账号：136***223
关卡：7/7　宝箱：6/6
图鉴：8/8　任务：7/7
本次获得：星声×100、贝币×60000、高级共鸣促剂×5、高级能源核心×5、高级共鸣回响×5
```

奖励顺序以接口实际返回顺序为准。已经完成的账号再次执行时，回复“本次没有新增奖励”。未完成关卡、未领取宝箱和未领奖任务会在结果中列出；满足条件后再次发送指令即可。接口返回新增资源 ID 时以资源编号显示，奖励数量统计仍保留。

## 账号与代理

插件在一个只读数据库会话中查询 XWUID 的绑定和账号记录。`WavesBind.uid` 中下划线分隔的第一个 UID 是当前选中账号。社区 token 查询同时限制 **UID、发送者 `user_id`、平台 `bot_id` 和 `game_id=3`**。

插件不会改写 XWUID 的绑定或 token。交换得到的活动凭据只保存在内存中。后台回复使用触发指令的会话快照，避免之后的消息改变回复对象。

每次运行读取以下 XWUID 配置：

| 配置 | 行为 |
|---|---|
| `KuroUrlProxyUrl` | 库街区 API 反代地址；为空时使用 `https://api.kurobbs.com` |
| `LocalProxyUrl` | 网络代理地址，支持代理自身的认证配置 |
| `NeedProxyFunc` | 包含 `all` 或 `run_activity` 时启用网络代理 |

库街区授权、活动登录和活动业务请求都使用已启用的网络代理。`KuroUrlProxyUrl` 仅替换库街区授权接口的基础地址；活动接口仍使用 `https://event-api.aki-game.com`。日志只记录网络代理是否开启。

## 执行、重载与错误处理

活动使用异步后台任务，指令处理函数提交开始提示后返回，因此关卡等待不占用 GsCore 的入站消息预算。同一 UID 从开始提示阶段起只允许一个活动任务，其他账号可以独立执行。

每个账号使用一个 `aiohttp.ClientSession`。单次请求超时为 30 秒；关卡等待使用 `asyncio.sleep`，不会阻塞事件循环。任务领取和关卡结算按顺序执行，写请求不自动重试。

每次领奖后查询任务状态，每次关卡结算后查询关卡状态。状态未更新时停止执行，避免继续提交。响应校验器在模块加载时创建并复用；已确认的列表用于后续判断，减少重复查询。

正常启动时，在接受机器人消息前注册指令；启动后的钩子不会重复注册。热重载只调用启动后钩子，因此同一注册函数也覆盖热重载，先取消名称以 `WavesActivity:` 开头的旧任务，再注册指令。关闭 GsCore 时也会取消任务，等待上限为 5 秒。被取消的开局不继续结算；服务端已完成的进度保留，重新发送指令可继续执行。被取消的任务不发送最终结果，取消事件会写入日志。

业务拒绝、HTTP 错误、网络超时、响应校验失败和非 JSON 响应会生成失败回复。其他后台异常记录异常类型和调用栈并回复管理员检查提示，不展开局部变量或任意异常正文，避免输出凭据。最终回复发送阶段独立记录失败，不将发送失败误报为活动接口失败。发送到平台后的实际投递由 GsCore 和适配器负责。

本次奖励统计只累计接口确认的首次结算奖励和成功领取的任务奖励。执行中途失败时，失败回复不包含完整的累计奖励；再次执行会跳过已经领取的奖励。接口领奖成功不等于已核对游戏邮箱到账。

## 常见问题

| 提示或现象 | 检查方法 |
|---|---|
| 当前账号未绑定有效 token | 使用 XWUID 登录指令，确认当前鸣潮账号有有效社区 token |
| 当前账号不在活动角色列表 | 更新 XWUID 登录，或切换到该 token 绑定的鸣潮账号 |
| 尚未参与活动 | 在活动网页完成该角色首次参与，再发送活动指令 |
| 活动尚未开始或已经结束 | 以活动配置接口状态为准，等待开放或更新下一期插件 |
| 该账号正在执行 | 等待已有任务完成；重复指令不会新建任务 |
| 网络请求失败或 HTTP 错误 | 检查 XWUID 网络代理和库街区 API 反代，恢复后再次执行 |
| 接口响应结构发生变化 | 查看日志，按新接口更新响应模型和流程 |
| 后台执行异常 | 查看 `[鸣潮活动] 后台执行异常` 后的堆栈 |
| 没有收到最终结果 | 检查任务是否重载取消，以及 GsCore、适配器连接和结果发送日志 |

## 源码结构

```text
WavesActivity/
├── __init__.py
├── __nest__.py
├── pyproject.toml
├── ruff.toml
├── pyrightconfig.json
├── .vscode/
├── README.md
├── CHANGELOG.md
├── DEPLOYMENT.md
├── REVIEW.md
└── WavesActivity/
    ├── __init__.py   # Plugins、SV、指令注册和生命周期钩子
    ├── runner.py     # 同账号互斥、后台任务和结果回复
    ├── bridge.py     # XWUID 只读账号查询和网络配置
    ├── activity.py   # 授权交换、活动请求和顺序执行
    └── models.py     # 响应模型、关卡参数和奖励汇总
```

插件通过内层入口显式导入上述模块，不使用 `__full__.py` 全目录扫描。开发时可用 `ruff check .` 和 `ruff format --check .` 检查代码；编辑器类型解析路径以插件安装在 GsCore 下为基准。
